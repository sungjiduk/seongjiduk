## 3. 기술 딥다이브 (5분) — "겪은 문제 3개로 말하는 아키텍처"

### 3-1. AI 모델, 뭐가 최선일까? — 실측 비교표 (1.5분)

**[슬라이드: 모델 비교표]**

| 모델 | 속도(34곳) | 품질 (같은 프롬프트) | 비용(1M tok, in/out) |
|---|---|---|---|
| gpt-4o-mini | ~수십초 | "소중한 추억을 쌓는 장소" — 어디에나 붙는 문장 | $0.15 / $0.60 |
| **gpt-4o ✅기본** | ~66초 | 칸다묘진 = 결성·연습 장면, 서비스 카피로 자연스러움 | $2.50 / $10.00 |
| gpt-5.5 | ~3배 느림 | **"μ's의 훈련 계단", "노조미(무녀) 인연"** — 덕후 전문가급 | (요금표 확인) |

> "그런데 재밌는 게, 처음엔 **5.5가 mini보다 못한 답**을 냈습니다. 환각 막으려고 '주어진 정보에만 근거하라'고 했더니, 5.5는 그 지시를 너무 잘 지켜서 자기가 아는 작품 지식까지 봉인하고 '정보가 제공되지 않았습니다'를 사용자 화면에 내보냈어요.
> 프롬프트를 '아는 지식은 활용하되 불확실한 세부만 생략'으로 바꾸자 위 표의 품질이 나왔습니다.
> **교훈: 프롬프트 제약은 모델 능력에 맞춰 조정해야 한다.** 그래서 정책은 — 라이브는 4o, 5.5는 나중에 백그라운드 사전 생성용." (ADR-0004)

### 3-2. GPT 비용이 2배로 새고 있었다 — single-flight (1.5분)

**[슬라이드: 로그 before/after]**

```
before: 프론트 fetch 2회(동시) → ai-service describe 수신 2회  ← 비용 2배
after : 프론트 fetch 2회(동시) → ai-service describe 수신 1회  ✅
```

> "설명은 성지별로 캐시하는데, **캐시가 비어있는 첫 순간에 동시 요청**이 오면 둘 다 미스가 나서 GPT를 두 번 부릅니다. React StrictMode가 개발 중에 이걸 상시 재현해줬죠(고마운 버그).
> 해결은 **작품별 락 + 락 획득 후 캐시 재확인** — 첫 요청만 GPT를 부르고 나머지는 기다렸다 캐시를 읽습니다. '두 번째는 그냥 건너뛰기'는 안 됩니다. 두 번째 응답이 화면에 남는 경우 설명이 사라지거든요.
> 동시성 테스트로 'Wanted 1 time, But was 2 times' RED를 먼저 만들고 구현했고, 실측으로 2회→1회 확인했습니다. 결과: **1차 조회 66초(생성) → 2차 0.05초(캐시), 비용 절반.**" (ADR-0005)

### 3-3. mock 테스트가 절대 못 잡는 버그 — h2c body 유실 (1.5분)

> "백엔드(Java)가 AI 서비스(Python/uvicorn)를 호출하는데, **body가 통째로 사라진 채** 도착해 422가 났습니다. curl로는 멀쩡했고요.
> 범인은 Java HTTP 클라이언트의 기본 동작 — 평문 http에 **HTTP/2 업그레이드(h2c)** 를 시도하는데 uvicorn이 이를 거부하면서 body가 유실됩니다. **HTTP/1.1 강제**로 해결했습니다.
> 이 버그의 포인트: 단위 테스트 74개가 전부 초록이어도 못 잡습니다. mock은 HTTP를 안 타니까요. 그래서 저희는 **통합 지점마다 실통신 E2E를 1회 이상 강제**하는 걸 원칙으로 삼았습니다." (트러블슈팅 로그)

## 4.5 확장성 — "검증된 루트가 상품이 된다" (1분)

> "지금은 Anitabi 좌표로 시작했지만, 데이터는 3단으로 진화합니다."

**슬라이드: 데이터 진화 3단 + B2B**

```
[1단] Anitabi 좌표          → 지금. 지도에 성지를 찍는 부트스트랩
[2단] 블로그 합의 신뢰도     → 네이버 공식 API로 후기 수집(원문 저장 X, 구조만 추출)
                             방문 순서를 스팟 시퀀스로 정규화 → 시퀀스 유사도 클러스터링
                             "○개 후기가 검증한 동선" 배지 — 여러 블로거가 같은 순서면 신뢰도 ↑
[3단] 자체 VisitRecord      → 우리 유저의 방문·체류 실측 = 독점·합법 데이터 플라이휠
```

> "이 3단이 쌓이면 결과물이 일정 텍스트가 아니라 **'팬 ○명이 검증한, 실이동시간이 계산된 코스'** — 즉 여행사가 바로 상품화할 수 있는 템플릿이 됩니다.
> 마이리얼트립 같은 플랫폼의 '현지 가이드' 자리에 **작품 캐릭터가 AI 가이드(캐릭터 보이스+아바타)로 붙는 투어 상품**까지가 저희가 보는 확장입니다 — 지금 만든 장면 설명 생성이 그 가이드 대사의 원천이고, Trip 도메인이 예약 스케줄의 밑단입니다. (캐릭터 IP는 판권사 제휴 전제)"

## 5. 마무리 (1분)

> "정리하면 — 성지덕은 ① 실데이터 파이프라인(임포트→지도→장면컷) ② 역할이 분리된 AI 레이어(설명·일정) ③ 비용·안정성 장치(캐시·single-flight·폴백)까지 **끝에서 끝까지 실제로 도는** 성지순례 플래너입니다.
> 다음 단계는 블로그 신뢰도 레이어와 이동시간 기반 고도화, 그리고 여행 상품 템플릿으로의 확장입니다. 감사합니다."

| GPT 환각으로 잘못된 장소 안내하면? | 좌표·순서는 도구 노드(코드)가 결정, LLM은 문장만. 불확실 세부는 생략하도록 프롬프트 정책화(ADR-0004). 출처 링크로 사용자 검증 가능 |
| AI 비용 관리? | 성지별 캐시 + single-flight로 중복 제거, 라이브=4o/CI·테스트=mock(무비용). 상용 시 DB 영속화+사전 생성 |
| 데이터 저작권? | CC BY-NC-SA 준수(출처표기·핫링크·비상업). 상용 전환 시 자체 데이터 교체 전제 |
| 왜 AI 서비스를 분리했나? | LangGraph 생태계가 Python 중심(ADR-0001). 장애 격리 — AI가 죽어도 본 서비스는 폴백으로 동작 |
