## 2. 서비스 소개 (1:00)
화면: 문제 / 해결 2카드

> "한 줄로, 성지덕은 **'덕후를 위한 성지순례 기반 AI 여행 플래너'**입니다.
> **문제부터.** 기존 여행앱은 연령·지역·패키지 같은 **일반 여행 기준**으로 설계돼 있어요. '내가 좋아하는 작품의 성지를 돈다'는 **콘텐츠 기반 여행**은 아무도 제대로 안 다룹니다. 코어 팬은 갈 곳을 이미 알아요. 문제는 **여러 성지를 이동순서·기간·예산으로 엮어 실제 일정으로** 만드는 과정이 고통이라는 거죠.
> **해결은 세 가지 조합** — 성지 데이터 + 지도 + AI 일정 생성. 작품·기간·예산·출발지 **최소 입력**만으로 동선을 짜고, 대화형으로 다시 조정하고, 저장·공유·예약까지 이어집니다."

## 6. ERD (0:50)
화면: ERD 4도메인

> "화면의 핵심 엔티티 14종, 네 덩어리입니다 — 사용자 / 콘텐츠·성지 / 여행 일정 / 기록·로그. 결제·예약 도메인까지 합치면 총 18종이고요.
> 설계에서 두 가지를 자랑하고 싶어요. 하나, **폴리모픽 FK 회피** — 일정의 한 정거장은 성지일 수도, 주변 관광지일 수도 있는데, 컬럼 하나로 두 테이블을 가리키면 외래키를 못 겁니다. 그래서 컬럼을 분리하고 타입으로 구분해 **참조 무결성**을 지켰습니다. 둘, 스키마는 **Flyway로 버전 관리**하고 운영은 `validate`로 — **엔티티와 스키마가 100% 일치할 때만** 뜨게 못 박았습니다."

화면(라이브): 성지 카드(한국어 설명·팁) + "여행자들이 검증한 코스"

> "각 성지엔 **GPT가 만든 한국어 설명·추천 체류시간·현장 팁**이 붙습니다. 핵심은 — **AI가 없는 장소를 지어내지 않아요.** DB에 있는 성지 안에서만 설명합니다.
> 그리고 여기, **여행자들이 검증한 코스.** 아무 블로그나 쓰는 게 아니라 **4단계 필터**를 통과해야 합니다 — 네이버 후기 검색 → **실제로 갔다 온 글만 통과시키는 실방문 게이트** → 우리 성지와의 스팟 매칭 → 여러 후기가 같은 순서로 돈 **동선 합의**. 실제로 러브라이브는 **후기 12건 중 실방문 인정이 단 2건**이었어요. 그 2건이 합의한 루트만 이렇게 랭킹으로 노출되고, **출처도 실제 블로그로 연결**됩니다. 근거가 없으면 안 보여주는 게 저희 원칙입니다."

## 14. 기술 해자 — Redis (1:20)
화면: Redis 성능 (66초→0.05초 · 6→107 · 18배)

> "저희는 외부 API를 굉장히 많이 부릅니다 — OpenAI, 구글, 네이버. 그런데 서버는 1대고 늘릴 수 없죠. 그래서 **Redis로 처리량과 비용을 방어**하는 걸 기술적 해자로 삼았습니다.
> 부하 테스트 결과입니다. 동시에 200개 요청이 몰릴 때, **아무 제어가 없으면 ai-service가 과부하로 무너져 성공이 6건**, 97%가 실패했어요. **Redis 동시성 가드를 붙이니 정상 처리가 107건, 약 18배**로 늘고, 자리 없는 요청도 에러 대신 안전하게 폴백해서 **사용자 에러는 0**. 서버를 늘려서가 아니라, **소프트웨어로** 만든 겁니다.
> 여기에 두 가지 더 — 네이버·구글 호출엔 **키별 분당 한도 레이트리미터**를 걸어 공유 키 차단과 과금을 방어하고, 이 가드 전체가 **fail-open**이라 **Redis 자체가 죽어도 서비스는 멈추지 않습니다.** 보호 장치가 새로운 장애 지점이 되면 안 되니까요."

## 예상 Q&A
1. **AI가 없는 성지를 지어내지 않나?** → 후보는 DB(Anitabi)에만 존재, LLM은 그 안에서 배치·설명만. 거리·순서는 코드.
2. **GPT 비용 관리는?** → Redis 캐시 + single-flight(66초→0.05초·비용 절반) + 레이트리미터.
3. **저작권은?** → 공식 이미지 저장 안 함. Anitabi(CC BY-NC-SA) 핫링크·출처 표기.
4. **왜 AI를 별도 파이썬 서비스로?** → LangGraph 생태계 + 부하·배포 분리. REST 계약 연동.
5. **테스트 전략?** → 레이어별 TDD, 통합 지점은 실통신 E2E 강제(단위테스트가 못 잡은 버그를 E2E로 발견).
6. **왜 어떤 작품은 검증 코스가 안 나오나?** → *"저희는 LLM이 그럴듯하게 지어낸 코스를 보여주지 않습니다. 실제 방문 후기가 검증한 코스만 노출하고, 근거가 없으면 안 보여주는 게 맞다고 판단했습니다. 각 코스에 출처 블로그 링크가 달려있는 이유입니다."* + 4단계 필터(검색→실방문 게이트→스팟 매칭→동선 합의) 어디서 걸렸는지로 설명. 빈약 결과는 30분 캐시 후 재수집이라 새 후기가 쌓이면 코스가 생길 수 있음.
7. **첫 조회가 느리지 않나?** → 첫 호출만 GPT 설명을 생성해서 느림(수십 초). single-flight 락으로 중복 호출을 막고 캐시 후엔 0.05초. 상용화 시 DB 컬럼으로 영속화 계획.
8. **Redis 장애 나면?** → 전 가드가 fail-open — 캐시는 미스로 간주하고 재계산, 리미터는 통과. 보호 장치가 새 장애 지점이 되지 않게 설계.
9. **검증 코스 데이터의 사업 가치는?** → 3번 슬라이드 B2B와 연결 — "팬 실방문이 검증한 루트"는 어디에도 없는 데이터 자산. 여행사 라이선스 대상.
10. **글로벌 작품(니지가사키)은 일정이 어떻게 되나?** → 500km 링크 지리 클러스터링으로 지배 지역만 일정에 담음(도쿄~오사카 국내 범위는 유지, 대륙 혼합만 차단). 출발지를 넣으면 출발지에서 가까운 지역이 선택됨.
