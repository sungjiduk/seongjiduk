## 0. 현재 진행상황 요약

### 배포/제품

- **정식 배포 완료**: https://holymoly.cloud EC2 실사이트 라이브.
- **데이터**: 4장르 15작품. 애니 11개 + 영화 2개 + 소설 1개 + K-POP 1개.
- **핵심 여정**: 작품 선택 -> 성지 지도 -> 검증 코스 -> 스탬프 선택 -> AI 일정 생성 -> 대화형 재조정 -> 미리보기/시사회 -> 저장/공유 -> 예약/결제 골격까지 관통.
- **AI**: LangGraph 3개 그래프(trip, route, describe). 라이브 provider는 OpenAI.
- **배포 안정화**: DDL validate + Flyway V1~V12, MySQL 볼륨 영속, Redis, Nginx Proxy Manager, GHCR 이미지 배포.

**멘트**

> "오덕후에게 여행은 관광이 아니라 순례입니다. 좋아하는 작품의 그 장면, 그 장소를 직접 밟는 것. 이걸 성지순례라고 부릅니다.

> 성지덕은 이 번거로움을 성지 데이터, 지도, AI로 해결합니다. 작품 하나만 고르면 실제로 갈 수 있는 성지순례 일정을 만들어줍니다."

> "바로 라이브 서비스에서 보여드리겠습니다."

## 4. 기술 딥다이브 - 원칙 하나와 문제 해결 (4분)

### 4-1. AI 원칙: LLM은 언어, 도구는 계산 (1분)

**화면**: LangGraph 3개 그래프 다이어그램.

**멘트**

> "AI 서비스는 LangGraph 상태머신 3개입니다.
>
> 첫 번째 trip 그래프는 일정 생성과 대화형 재조정을 합니다. 필터링, 제약 변환, 2-opt 동선 최적화, 출발지 앵커링, 이동시간 모델을 거칩니다.
>
> 두 번째 route 그래프는 네이버 후기를 읽고 실제 방문 순서만 추출한 뒤, 여러 후기의 공통 동선을 클러스터링합니다.
>
> 세 번째 describe 그래프는 성지별 한국어 이름, 추천 체류시간, 장면 설명, 현장 팁, 미션 초안을 만듭니다.
>
> 핵심은 역할 분리입니다. GPT는 판단과 언어만 맡고, 좌표와 이동시간과 집계는 코드가 처리합니다. 그래서 환각이 장소 좌표를 건드리지 못합니다."

### 4-2. 차별화: 블로그로 검증된 동선 만들기 (1분)

**멘트**

> "일정 순서를 AI가 상상하면 신뢰가 약합니다. 그래서 실제 방문 후기를 검증 재료로 씁니다.
>
> 네이버 검색 API로 후기 후보를 가져오고, 본문은 원문을 저장하지 않고 구조만 추출합니다. GPT가 이 글이 실제 방문 후기인지 먼저 게이트를 통과시키고, 방문 순서를 뽑습니다. 그다음 코드는 방향을 무시한 연속쌍 합의로 여러 사람이 독립적으로 비슷하게 돈 코스를 찾습니다.
>
> 저희 데이터는 Anitabi 좌표에서 시작해, 블로그 합의 동선, 그리고 나중에는 우리 유저의 VisitRecord로 진화합니다. 이게 성지덕의 데이터 해자입니다."

### 4-3. 비용이 새던 문제: single-flight (0.7분)

**멘트**

> "캐시가 비어 있는 첫 순간 동시에 요청이 들어오면 둘 다 GPT를 호출합니다. React StrictMode나 여러 사용자가 동시에 누르는 상황에서 비용이 두 배로 새는 구조였습니다.
>
> 그래서 Redis 락으로 작품별 single-flight를 걸었습니다. 첫 요청만 GPT를 부르고, 나머지는 락 해제 뒤 캐시를 다시 확인해 같은 결과를 재사용합니다.
>
> 실측으로 첫 호출 66초, 두 번째 호출 0.05초. 같은 결과를 GPT 두 번 부르던 비용도 절반으로 줄었습니다."

### 4-4. 운영에서 잡은 장애: 배포와 CI (0.7분)

**멘트**

> "라이브 배포 후 실제 장애도 잡았습니다. AI 컨테이너가 계속 재시작됐는데, 원인은 Dockerfile이 새로 추가된 route_graph.py를 복사하지 않은 것이었습니다. `COPY *.py`로 바꾸고 ai-service를 정상화했습니다.
>
> 또 startLocation이 null이면 422가 나던 문제를 Optional로 바꿨고, Maven Central 403 플레이크는 Docker build 단계에 백오프 재시도를 넣었습니다. 지금은 4개 repo CI가 green입니다."

## 7. 기술 해자 - Redis/TPS 수치 자리 (1분)

**확정 수치**

- single-flight: 첫 호출 66초 -> 캐시 재사용 0.05초.
- 동일 캐시 미스 중복 상황에서 GPT 호출 2회 -> 1회, 비용 절반.

**TPS 벤치 수치 입력 자리**

| 지표 | Redis 적용 전 | Redis 적용 후 | 개선 |

**멘트**

> "외부 API는 느리고, 돈이 들고, 429 제한이 있습니다. 그래서 캐시, single-flight, 동시성 제한 큐, 레이트리미터를 Redis로 묶어 같은 서버에서도 비용과 처리량을 제어하는 구조를 만들고 있습니다.
>
> 벤치 수치가 완료되면 이 표를 채우고, 없으면 오늘은 확정된 single-flight 수치까지만 말하겠습니다."
