# 01. 아이디어 초안 (브레인스토밍)

> 목적: 요구사항 5대 필수(회원/OAuth · 영속화 · UI · AI 에이전트 · 관리자 통계)를
> **모두** 자연스럽게 충족하는 주제 선택. UI/UX는 평가 대상이 아니므로 "기능이 결함 없이 동작"에 유리한 주제가 좋다.
> 아래 후보 4개를 디벨롭해 두었음. 팀 논의 후 하나 골라 `02_최종_기획서.md`로 옮긴다.

## 선택 기준 (왜 이게 중요한가)
- **AI 에이전트가 서비스의 중심이어야** 함. AI가 "곁다리 챗봇"이면 LangGraph를 쓸 명분이 약해진다.
  - 비유: AI를 *엔진*으로 둘지, *에어컨*으로 둘지의 차이. 평가에선 엔진이 유리하다.
- 도메인이 단순해야 11일 안에 끝난다. 화면은 못생겨도 되니 **데이터 흐름이 명확한** 주제가 좋다.
- 통계가 자연스럽게 나오는 주제(= 사용자 행동이 또렷한 주제)가 관리자 기능 구현을 쉽게 만든다.

---

## 후보 A. AI 회고/일기 + 감정 분석 서비스
- **한 줄**: 사용자가 일기를 쓰면 AI가 요약·감정 분석하고 주간 리포트를 만들어 준다.
- **AI 에이전트**: 일기 입력 → 감정 분류 → 키워드 추출 → 주간 요약 생성 (LangGraph 멀티스텝에 딱 맞음).
- **통계 친화도**: 작성 빈도, 감정 분포, 활성 사용자 → 관리자 통계로 자연스럽게 연결.
- **DB**: 일반 RDB로 충분 (감정 추세 저장). 벡터 불필요.
- **난이도**: 낮음~중. 도메인 단순, AI 비중 높음.
- **리스크**: 데이터가 적으면 통계가 빈약해 보일 수 있음(시드 데이터 필요).

## 후보 B. 문서 기반 RAG Q&A 챗봇 ("사내 위키 봇")
- **한 줄**: 사용자가 문서(PDF/텍스트)를 올리면 그 문서에 근거해 질문에 답하는 챗봇.
- **AI 에이전트**: 질문 → 검색(RAG) → 근거 종합 → 답변 + 출처 (LangGraph + 벡터검색의 정석).
- **통계 친화도**: 질문 수, 문서 수, 인기 질의 → 통계 풍부.
- **DB**: PostgreSQL + **pgvector** (벡터 검색). 요구사항 벡터 DB 항목과도 맞물림.
- **난이도**: 중. RAG/임베딩 파이프라인 구축 필요하지만 LangGraph 활용도가 가장 높음 = **평가 어필 강함**.
- **리스크**: 임베딩/청킹 품질 튜닝에 시간 소요.

## 후보 C. AI 레시피 추천 ("냉장고 파먹기")
- **한 줄**: 보유 재료를 입력하면 AI가 만들 수 있는 레시피를 추천/생성.
- **AI 에이전트**: 재료 파싱 → 후보 검색 → 부족 재료 계산 → 레시피 생성 (도구 호출형 그래프).
- **통계 친화도**: 인기 재료/레시피, 추천 클릭률 → 통계 가능.
- **DB**: RDB + (선택) 레시피 임베딩 검색.
- **난이도**: 중. 레시피 데이터 확보가 관건.
- **리스크**: 데이터 출처/품질. AI 생성에 의존하면 결과 편차.

## 후보 D. AI 여행 일정 플래너
- **한 줄**: 목적지·기간·취향 입력 → AI가 day-by-day 일정 생성, 수정 대화.
- **AI 에이전트**: 조건 수집 → 장소 후보 → 동선 최적화 → 일정 생성/수정 (대화형 멀티턴, LangGraph 적합).
- **통계 친화도**: 인기 목적지, 생성 수, 재방문 → 통계 가능.
- **DB**: RDB. (장소 외부 API 연동 시 범위 커짐)
- **난이도**: 중~상. 외부 데이터/API 붙이면 일정 압박.
- **리스크**: 11일 안에 "동선 최적화"까지 가면 과욕. 범위 축소 필요.

## 추천
- **1순위: B (RAG Q&A 챗봇)** — LangGraph·벡터DB를 정면으로 쓰는 주제라 기술 요구사항과 가장 잘 맞고, AI가 서비스의 *엔진*이 된다. pgvector를 쓰면 DB 요구사항도 함께 해결.
- **안전책: A (AI 일기/감정)** — 도메인이 단순해 11일 일정에 가장 안전. 데모가 깔끔하게 떨어진다.
- 팀 성향이 "확실한 완성" 쪽이면 A, "기술 어필" 쪽이면 B.
