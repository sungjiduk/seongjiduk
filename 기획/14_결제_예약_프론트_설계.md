# 14. 예약·결제 프론트엔드 설계 (Toss Payments)

> 루트 확정 → 항공·숙소 상품(offer) 견적 → 주문 → Toss 결제창 → 승인·자동예약.
> 팀원 백엔드 `feat/payment`(TravelOffer·PaymentOrder·Payment·SupplierBooking) 계약에 맞춘 **프론트엔드** 설계.
> 결정일: 2026-07-09. VISION ⑨(최종 확정 → 결제 → 연동 API 자동 예약)의 프론트.

## 0. 확정 결정
- **실 PG = Toss Payments 테스트 모드**: 실제 결제창·테스트 카드로 전 흐름 동작, **실돈 X**. 실 라이브 키 전환은 추후 사용자.
- ⚠️ **실제 결제 실행은 사람이 수행**(테스트 카드 입력 등) — 자동화가 실결제를 실행하지 않는다.
- 흐름 형태 **A(전용 예약·결제 플로우)** + Toss **requestPayment(리다이렉트)** 방식.
- 백엔드는 팀원 `feat/payment`가 완성(미머지). 프론트는 그 계약에 맞춰 선구현, 머지+Toss 테스트 키 설정 후 라이브 실증.

## 1. 백엔드 계약 (feat/payment, 원문 기준 — 프론트가 소비)
전부 `{success, data, error}` 래핑, **JWT 인증 필수**.

| 메서드 | 경로 | 요청 | 응답(data) |
|--------|------|------|-----------|
| GET | `/api/trips/{tripId}/offers` | - | `{ flights: TravelOffer[], hotels: TravelOffer[] }` |
| POST | `/api/payment-orders` | `{ tripPlanId, offerIds:number[] }` | `{ orderId, orderName, amount, currency, clientKey }` |
| POST | `/api/payments/confirm` | `{ paymentKey, orderId, amount }` | `{ orderId, status, paymentKey, method, amount, currency, receiptUrl, supplierBookings[] }` |

- `TravelOffer = { offerId:number, provider, offerType:'FLIGHT'|'HOTEL', name, description, price:number, currency, validUntil }`
- `SupplierBooking = { provider, externalReservationId, status, paidAmount, currency }`
- `PaymentOrderStatus`: READY·PAYMENT_DONE·BOOKING_REQUESTED·**BOOKED**·FAILED·CANCELED·REFUNDED.
- **clientKey는 주문 생성 응답으로만 내려온다** → 프론트 env에 Toss 키 불필요. secretKey는 백엔드 전용(confirm 시 서버가 Toss와 통신).

## 2. 프론트 흐름·화면
1. **진입**: TripResult에 "🧳 예약·결제" 버튼(저장/공유 옆). offers가 인증 필수라 비로그인 시 기존 탑승수속(AuthModal, TripResult의 `authFor`) 재사용.
2. **견적 `BookingFlow`**(오버레이/뷰): `fetchTripOffers(tripId)` → 항공 리스트·숙소 리스트. 라디오로 항공 1·숙소 1 선택(선택 사항 조합은 offerIds 배열), **하단 실시간 합계**. 여정 경비(교통·식사)는 참고 안내만(결제 대상 아님). "₩N 결제하기".
3. **주문·결제**: `createPaymentOrder(tripPlanId, offerIds)` → `{orderId, orderName, amount, clientKey}`. `@tosspayments/tosspayments-sdk`의 `loadTossPayments(clientKey)` → `payment.requestPayment({ method:'CARD', amount:{currency:'KRW', value:amount}, orderId, orderName, successUrl, failUrl })` → Toss 결제창.
4. **복귀·승인**: 앱이 라우터 없이 상태기반 → **쿼리파라미터로 랜딩 감지**. `successUrl = ${location.origin}${basePath}?pay=success`, `failUrl = ...?pay=fail`. App 마운트 시 `pay` 파라미터 감지:
   - `success` → `PaymentResult` 뷰: URL의 `paymentKey·orderId·amount`로 `confirmPayment(...)` → 결과(`status:BOOKED`, 예약 카드=supplierBookings, 영수증 링크=receiptUrl). confirm 성공 후 URL 쿼리 정리(중복 confirm 방지).
   - `fail` → 실패 안내 + 재시도.

## 3. 코드 구조 (seongjiduk-frontend)
- `src/api.ts`: `TravelOffer/TravelOffers/PaymentOrder/PaymentConfirm/SupplierBooking` 타입 + `fetchTripOffers(tripId)`·`createPaymentOrder(tripPlanId, offerIds)`·`confirmPayment(paymentKey, orderId, amount)` (전부 `auth:true`).
- `src/payment/BookingFlow.tsx` — 견적·선택·결제 시작 오버레이. props: `{ tripId, tripPlanId, onClose }`(tripId=tripPlanId 동일하나 계약 필드명 유지).
- `src/payment/PaymentResult.tsx` — 리다이렉트 복귀 confirm·결과.
- `src/payment/toss.ts` — Toss SDK 로드 헬퍼(`requestTossPayment(order, successUrl, failUrl)`), SDK 격리.
- `src/payment/payment.css` — 토큰 기반 스타일(--rail/--hanko/--card/--radius-lg 등).
- `src/App.tsx` — 마운트 시 `?pay=` 감지 → PaymentResult 분기(1곳).
- `src/views/TripResult.tsx` — "🧳 예약·결제" 진입 버튼.
- **의존성**: `@tosspayments/tosspayments-sdk`(공식 v2) 1개 추가.

## 4. 안전·정합·에러
- **테스트 모드 전용**: clientKey=Toss 테스트 클라이언트 키(백엔드 env). 실돈 안 나감.
- **금액 무결성**: 프론트는 주문 응답 amount를 그대로 requestPayment·confirm에 전달, 백엔드가 Toss와 재검증 — 프론트 금액 조작 불가.
- **에러 처리**: offers 빈/만료·주문 실패·confirm 실패 각각 사용자 메시지. 실패 리다이렉트 처리. **중복 confirm 가드**(새로고침 시 파라미터 소진·상태 확인). UnauthorizedError → 탑승수속.
- **검증(레포에 테스트 러너 없음)**: `npx tsc -b` + `npx vite build` + `VITE_MOCK`/실백엔드 브라우저. Toss 실동작은 백엔드 머지+테스트 키 후 라이브. devMock에 offers/order/confirm 목 라우트 추가해 UI는 백엔드 없이도 확인.

## 5. 전제·순서
1. 프론트 선구현(계약 기준) — 팀원 `feat/payment` 머지 대기 병행.
2. 백엔드 머지 + Toss **테스트 키**(`TOSS_CLIENT_KEY`/`TOSS_SECRET_KEY`) 설정 → 라이브 실증(주문→결제창→테스트카드→BOOKED).
3. 실 라이브 키 전환·정산은 발표 후·사용자 액션(법·PG 이슈).
